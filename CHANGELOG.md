# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **BREAKING:** the minimum TinyDB version is now 4.9.0 (was 4.8). TinyDB 4.9.0 drops Python 3.8/3.9 — no change for tinydantic, whose floor is already 3.10 — and changes one behavior tinydantic depends on: `Table.update(doc_ids=…)` and `Table.remove(doc_ids=…)` now **silently skip** ids that are not in the table and return only the ids they touched, where 4.8 raised `KeyError` partway through ([upstream #591](https://github.com/msiemens/tinydb/issues/591)). That turns a mixed batch into a partial write that reports success, so tinydantic's up-front existence check — previously a way to trade a bare `KeyError` for a curated one — is now what keeps `update()`/`remove()` all-or-nothing, and is covered by new tests on both the validated and `validate_writes=False` paths. Three upstream fixes are inherited with no tinydantic change: `YAMLStorage(path, create_dirs=True)` now works for a bare relative filename like `"db.yaml"` (TinyDB's `touch()` helper called `makedirs("")` and raised `FileNotFoundError`; [#619](https://github.com/msiemens/tinydb/pull/619)), `Query.test()` accepts unhashable arguments such as lists and dicts instead of raising `TypeError` at the query cache ([#517](https://github.com/msiemens/tinydb/issues/517)) — which also means composed conditions containing one keep the hashval tinydantic's id-condition detection reads — and `LRUCache` no longer mishandles falsy cached values ([#596](https://github.com/msiemens/tinydb/issues/596)), which for tinydantic means a query whose result set is empty is now cached as effectively as any other.
- The `cast("Callable[[Mapping], None]", ...)` band-aids around every `Table.update()`/`Table.update_multiple()` call are gone, along with an internal `cast("dict[str, Any]", ...)` inside the revision-rotation wrapper. TinyDB 4.9.0 retyped the transform parameter as `Callable[[MutableMapping], None]` ([#621](https://github.com/msiemens/tinydb/pull/621)), which is the signature tinydantic's own `replace()` operation already advertised — the previous annotation rejected a correctly-typed transform under parameter contravariance, so the working call was the one that failed to type-check. `get()` now dispatches to TinyDB's new per-shape `Table.get()` overloads instead of forwarding three optional selectors, which types each branch precisely. The corresponding entries move to [Upstream Limitations → Resolved upstream in TinyDB](https://tinydantic.dev/contributing/upstream_limitations/#resolved-upstream-in-tinydb).

- **BREAKING:** A query condition used where a boolean belongs now raises the new `QueryConditionError` (a `TinydanticUserError` and a `ValueError`, matching `FindQueryError` and the numpy/pandas ambiguous-truth precedent) instead of being silently, permanently true. `bool(User.name == "Alice")` was `True` — and so was `bool(User.name == "nobody")`, because a condition is an object describing a test, not a comparison. Nothing raised, so `if User.name == requested:` read like an existence check, passed review, and never touched the table; `and`/`or` silently discarded half a composed query (keeping the right and left operand respectively); `not` returned a plain `False`; `any()`/`all()` collapsed a list of conditions to `True`; and a class-level condition in a comprehension filtered nothing. Two adjacent holes close with it: `"A" in User.name` was `True` for any operand (`Query` defines `__getitem__` but no `__iter__`, so Python's legacy sequence protocol iterated the query and compared against a freshly built — and truthy — condition), and `User.tags[0] == "red"` matched nothing forever (TinyDB reads a non-string path step as a callable to apply, so the index raised internally and was swallowed). Iteration and non-string path steps are now refused as well, each with a message naming the query that expresses the intent: `contains()`/`get()`/`exists()` for existence, `&`/`|`/`~` for composition, `.search()`/`.test()`/`.any()` for membership, `instance.field` for comparing a value you already hold, and `cond is not None` for the one benign idiom the guard breaks — optional-filter builders that used truthiness to mean "was a condition set". The guards ride on the objects tinydantic hands out (`Model.field`, `q()`, `field()`, `Model.id`, and anything composed from them); a raw `tinydb.Query()` you build yourself keeps TinyDB's behavior. Guarded conditions remain ordinary `QueryInstance` subclasses — same test, same hashval, same equality — so they still compare, hash, cache, and compose interchangeably with raw TinyDB conditions. The mechanism and the upstream changes that would remove it are recorded on the [Upstream Limitations](https://tinydantic.dev/contributing/upstream_limitations/) page.
- `q()`'s `TypeError` now names the exact call to make for the two mistakes that carry enough information to identify themselves. Handed a shadowed field's method (`q(Command.search)`) it said "reach for the value on an instance" — advice with no instance to reach for, and never mentioning `field()`, which the Queries page documents as the fix for precisely that case; it now recovers the attribute's name and its owning class and says `field(Command, 'search')`. Handed a plain (non-`computed_field`) property it gave the same generic line; it now explains that a plain property is not serialized, so no document key exists to match, and points at `@computed_field` as the way to make it queryable. That branch became unambiguous only because computed fields now resolve to a `Query`, so any `property` reaching the hint is necessarily the kind that is never stored.
- Docs: the Queries page's `q()` traceback example had drifted — it still promised the pre-`field()` message ("or a field name string") that `q()` stopped accepting. It escaped notice because the project runs doctests with `IGNORE_EXCEPTION_DETAIL`, which compares only the exception type, so the example could say anything and still pass. The example now disables that flag inline (`# doctest: -IGNORE_EXCEPTION_DETAIL`), so the advice in the docs is checked against the advice the code actually gives.

- **BREAKING:** `q()` no longer accepts a field name string — it is a cast and nothing else, raising `TypeError` for anything that is not a TinyDB `Query`. The string form could not be made safe: `q("search")` (a field-name literal) and `q(user.name)` (an instance attribute that happens to hold a string) are the same call with the same runtime information, so the second silently built a query on the _value_ (`where("Alice")`) and matched nothing forever — while the docstring promised a `TypeError` for exactly that mistake. Migration is mechanical and fails loudly: `q("name")` becomes `field(Model, "name")`, or `tinydb.where("name")` for a key your model does not declare. `ShadowedFieldError`'s message now names `field()` accordingly.

- **BREAKING:** `find` is now a reserved attribute name on tinydantic models (flat-namespace policy). A model with a field named `find` raises `ShadowedFieldError` at class definition; opt out with `shadowed_fields=("find",)` or rename the field (opting out forgoes the `find()` entry point on that model — `search()` still works).

- Docs: static type checking is now introduced where users first meet it. The quickstart gained an "If you use a type checker" section explaining why `User.name == "Alice"` types as `bool`, showing the `q()` form, and warning that suppressing the error on an overloaded method (`get()`, `get_or_raise()`, `find()`) costs mypy the return type entirely. The Queries page documents what `q()` does _not_ fix — expressions like `User.name.upper()` that satisfy a checker and fail at runtime — and that `q()` raises rather than shrugging when handed a shadowed field's method. Examples throughout the docs deliberately keep the bare form; `q()` is opt-in, and the reasoning (along with the rejected `Mapped[T]` and mypy-plugin alternatives) is recorded in the new [Static typing design](https://tinydantic.dev/contributing/static_typing/) page.
- CI now runs both mypy and pyright (`poe types` runs the pair; `pyright` joins the `types` dependency group). Neither checker had been gating anything: `poe types` was a local-only task. The two disagree in ways that matter here — pyright preserves a return type where mypy falls back to `Any` — so the query-typing contract is pinned against both by the new `tests/static_typing/` suite, which asserts inferred types rather than running assertions.

- Docs: the FastAPI guidance now documents the single-threaded contract explicitly and inverts the previous recommendation — `async def` handlers calling `tinydantic` inline (Pattern A: single-threaded by construction) replace plain `def` threadpool handlers as the default, with a single-worker executor (Pattern B) for when the event loop must stay responsive, and criteria for moving from A to B. Plain `def` handlers and `asyncio.to_thread` offloading are now documented as contract-breaking. `revision_id` joins `id` as a name `tinydantic` can manage on models (only with `use_revision=True`; without it the name stays yours).
- **BREAKING:** `PyYAML` is no longer a default dependency — `YAMLStorage` now lives behind the `yaml` extra. Existing YAMLStorage users: `pip install tinydantic[yaml]` after upgrading (constructing `YAMLStorage` without it raises an `ImportError` naming that exact command; plain `import tinydantic` never needs PyYAML).
- **BREAKING:** the `pydantic[email]` extra was dropped from the dependencies — nothing in tinydantic uses it. To use `EmailStr` fields in your models, install `pydantic[email]` yourself. The quickstart example now demonstrates an `age: int` field instead.

- **BREAKING:** `before_write` and `after_read` are now reserved attribute names on tinydantic models (reserved words #27 and #28 under the flat-namespace policy). A model with a field of either name raises `ShadowedFieldError` at class definition; opt out with `shadowed_fields=` or rename the field.

- **BREAKING:** `patch` is now a reserved attribute name on tinydantic models — the first method added under the flat-namespace policy. A model with a field named `patch` raises `ShadowedFieldError` at class definition; opt out with `shadowed_fields=("patch",)` or rename the field.

- **BREAKING:** A model field whose name shadows an existing class attribute — a tinydantic method (`search`, `count`, ...), a pydantic method (`copy`, `json`, ...), or a method from your own base classes — now raises `ShadowedFieldError` at class definition instead of pydantic's easily-missed warning followed by silently broken `Model.field` query sugar. Opt in deliberately with the new `shadowed_fields=("name", ...)` class kwarg (inherited like the other config keys) and query such fields with `q("name")`.

- **BREAKING:** Selector misuse raises the new `SelectorError` (a `ValueError` subclass, so existing handlers keep working): zero-selector `get()`/`contains()`/`remove()` no longer leak TinyDB's `RuntimeError`, `upsert()` without a cond or a persisted `id` no longer leaks TinyDB's `ValueError` (whose "use a table.Document" hint means nothing in tinydantic), and the existing too-many-selector `ValueError` guards are upgraded to `SelectorError`. `remove()` with no selector points at `truncate()`.
- **BREAKING:** `insert()`/`insert_multiple()` with an already-taken `id` raise the new `DocumentAlreadyExistsError` (also a `ValueError` subclass) naming the model, table, and taken id(s) — including ids repeated within one batch — instead of TinyDB's raw `ValueError`.
- **BREAKING:** `update()`/`remove()` with an explicit `doc_ids` list containing a missing id raise `DocumentNotFoundError` (matching `replace()`/`delete()`) and abort before anything is written. Against TinyDB 4.8 this replaced a bare `KeyError`; against 4.9 it replaces something worse — see the minimum-version entry below.
- **BREAKING:** Attribute assignment is now validated (`validate_assignment` in the base `model_config`): assigning a value that fails validation raises `pydantic.ValidationError` immediately, and `model_validator(mode="after")` invariants re-run on every assignment. Subclasses can opt out with `model_config = ConfigDict(validate_assignment=False)`.
- **BREAKING:** Whole-model writes (`insert()`, `insert_multiple()`, `save()`, `replace()`, `upsert()`) validate their serialized payload before it reaches storage and raise `pydantic.ValidationError` for documents that would fail on their next read — closing the paths assignment validation cannot see (in-place container mutation, nested-model mutation, `object.__setattr__`). Opt out per model with the new `validate_writes=False` class kwarg.
- **BREAKING:** `update()` and `update_multiple()` validate each matched document's merged result (stored body plus new fields, or a transform callable's output) with the real document id visible to validators, before anything is written; a validation failure anywhere aborts the whole batch with nothing written. Transform callables can no longer write schema-invalid data by default; `validate_writes=False` restores the previous behavior. All mapping/transform updates now run through the atomic write cycle previously reserved for id-condition writes.
- **BREAKING:** Update mappings containing keys that are not model fields raise the new `UnknownUpdateFieldError` instead of writing them to storage unvalidated. Pass `extra_keys="allow"` to `update()`/`update_multiple()` to write them anyway (for databases shared with other tools or schema-evolution keys the model does not know yet).
- **BREAKING:** `YAMLStorage.write` now serializes with `yaml.safe_dump` (matching the `yaml.safe_load` used by reads) and raises `yaml.representer.RepresenterError` for values the safe dumper cannot represent — before the file is touched. Previously, full-Dumper `yaml.dump` wrote arbitrary Python objects as `!!python/object` tags that the storage's own read then refused to load, leaving the database file unreadable until hand-edited.
- **BREAKING:** `SortIntDocIDsMiddleware` no longer overwrites the wrapped storage's `sort_keys` setting — it pre-sorts the data instead (documents by numeric `doc_id`, tables by name). Field order inside each document now follows the storage's own configuration: insertion order for `JSONStorage` (previously force-alphabetized), PyYAML's default sorting for `YAMLStorage` unless you pass `sort_keys=False`. Existing JSON files re-serialize with reordered fields on the next write — a one-time diff, not a data change. The middleware also no longer requires the wrapped storage to expose dump kwargs at all, so it now works with `MemoryStorage` and other kwargs-less storages.
- `model_validator(mode="after")` hooks now observe the document's real `id` during reads (previously always `None`), and a stray legacy `id` key inside a stored document body is always masked by the actual `doc_id`.
- The defensive fallthrough in `get()` for a contract-violating TinyDB `Table.get()` return now raises a `TypeError` naming the unexpected type instead of a bare, message-less one.
- **BREAKING:** `UniqueConstraintError`'s constructor now takes `fields`/`values` tuples (plus an optional `comparison_key`) instead of the singular `field`/`value` keywords, so one error type covers single-field markers and composite constraints. Messages for single-field violations are unchanged; only code constructing the error directly is affected.
- The code license is now MIT only (previously dual-licensed under Apache-2.0 OR MIT). The relicense is not retroactive: released versions up to and including 0.4.0 remain available under Apache-2.0 OR MIT. Documentation and images remain CC-BY-4.0.
- `model_config["protected_namespaces"]` now restates Pydantic's own default alongside tinydantic's prefix — `("tinydantic_", "model_validate", "model_dump")` where it was `("tinydantic_",)`. Setting the key _replaces_ the inherited value rather than extending it, so reserving the `tinydantic_` prefix had been silently discarding Pydantic's forward-compat protection: a field named `model_dump_toml` drew a `UserWarning` on a plain `BaseModel` and nothing at all on a tinydantic model. Names that collide with an attribute that exists today were never at risk (tinydantic's own `ShadowedFieldError` is stricter than Pydantic's namespaces there), but a field named for a method a future Pydantic adds would have gone unflagged until the upgrade that broke it. A tinydantic model is now never less protected than the plain `BaseModel` it replaces, and a new test reads the default out of Pydantic so a release that reserves a new prefix fails the suite rather than quietly losing the protection.
- Docs: the **TinyDB Limitations** contributing page is now **[Upstream Limitations](https://tinydantic.dev/contributing/upstream_limitations/)** (`docs/contributing/tinydb_limitations.md` → `upstream_limitations.md`), with one section per upstream project — each carrying its own private-API registry and resolved-upstream log. The TinyDB material is unchanged; a Pydantic section joins it, covering the `model_config` merge order that drives tinydantic's separate `__tinydantic_config__` ([pydantic#9992](https://github.com/pydantic/pydantic/issues/9992), open), the `protected_namespaces` replacement semantics behind the fix above, the type-checking-only dependency on `pydantic._internal._model_construction.ModelMetaclass`, and the `model_` default narrowed in Pydantic 2.10 ([pydantic#10315](https://github.com/pydantic/pydantic/issues/10315)) that tinydantic inherits at its 2.11 floor.

### Added

- Computed fields are now queryable through the `Model.field` shorthand: `Product.price_band == "budget"` builds a real TinyDB query instead of silently evaluating to `False`. `field(Model, name)` already accepted computed fields (they are serialized, so they reach storage as ordinary document keys), but attribute access could not reach them — pydantic leaves a computed field as a real class attribute, so ordinary lookup succeeds and the metaclass `__getattr__` that powers `Model.field` never fires. Class-level access now resolves through a descriptor, which sees the distinction `__getattr__` cannot. Instance access (`user.price_band`), serialization, JSON schema, and inheritance are unchanged, and computed fields stay read-only: assignment is routed to the wrapped property, so a computed field with a setter still runs it and one without still raises the interpreter's own `AttributeError` (whose wording CPython changed in 3.11). Frozen models are left to pydantic's own frozen-instance error. Ordinary (non-`computed_field`) properties are deliberately untouched — they are not serialized, so a query on one could never match.

- `field(Model, "name")` and `QueryFieldError` — the named-field query form split out of `q()`, and validated rather than trusted. Accepts the model's fields plus its computed fields (pydantic serializes those, so they reach storage and are genuinely matchable); refuses storage aliases (matching `sort()`'s Python-field-names policy), dotted paths (`where()` does not traverse them — the message points at attribute chaining), and `id`, which is in `model_fields` but maps to `doc_id` and is never written to the document body, so a body query on it returned `[]` forever. The returned condition is an ordinary TinyDB query — equal to and hashing as `where(name)` — so the model is a build-time lookup table only and conditions stay interchangeable with raw TinyDB. Keys your model does not declare (`extra='allow'` documents, legacy keys) are not enumerable at class level and remain reachable with `tinydb.where()`, which the error message names.
- `Model.find()` fluent query API: lazy, immutable `FindQuery` chains with `sort()`/`skip()`/`limit()` modifiers, read terminals (`all()`, `first()`, `first_or_raise()`, `count()`, `exists()`, iteration), and write terminals (`delete()`, `update()`) that honor the sorted window by resolving it to document ids — `X.delete()` removes exactly what `X.all()` returns, unlike Beanie, which silently ignores sort/skip/limit on writes. `find()` with no argument is the explicit whole-table spelling; `find(None)` raises `SelectorError` so a condition variable that is unexpectedly `None` can never silently widen a query. Repeating a modifier raises the new `FindQueryError` (the ecosystem disagrees on what a second `sort()` means — Beanie appends a tiebreaker, Python's stable-sort idiom and pandas make the last sort primary, Django and MongoEngine replace — so tinydantic refuses to guess); unknown sort fields raise the new `SortFieldError` eagerly at the `sort()` call.
- Optimistic concurrency: the `use_revision=True` class kwarg (inherited like the other config keys; not late-bindable via `bind()`) injects a `revision_id: UUID | None` field — an opaque token minted on insert and rotated by every write path. `save()`, `replace()`, and `delete()` compare the instance's held token against storage first and raise the new `StaleDocumentError` (with a `deleted` attribute distinguishing concurrently-deleted from modified — a revisioned `save()` no longer silently resurrects a deleted document) when another writer got there in between; each takes `ignore_revision=True` for deliberate last-write-wins. `patch()` and the table-level verbs (`update()`, `update_all()`, `update_multiple()`, `upsert()`) rotate without checking. Writing `revision_id` directly through an update mapping or `patch()` raises the new `RevisionUpdateError`; declaring your own `revision_id` field on a revisioned model raises the new `RevisionFieldError` at class definition. Documents written before the opt-in are adopted conflict-free on their first revisioned write.
- `ProcessLockMiddleware` — opt-in enforcement of TinyDB's single-process contract: takes a non-blocking exclusive OS advisory lock on a `<database path>.lock` sidecar at open and raises the new `DatabaseLockedError` immediately when the database is already open in another process (or a second TinyDB instance in this one), turning slow multi-process corruption into a startup error. The OS releases the lock on process death; detection only — it does not make multi-process access safe.
- Docs: a "Concurrency" usage page — the single-process/single-thread contract and why (TinyDB has no locks and its caches assume sole ownership), the cross-request stale-write window, the full `use_revision` protocol with a doctested `ETag`/`If-Match`/`412` FastAPI flow, `ProcessLockMiddleware`, backup/restore semantics (restores fork history; revision tokens catch reused-`doc_id` imposters on writes; a stable-`uid` recipe for external references), and an honest list of what remains unguarded.
- Docs: a "Schema evolution" usage page — the unknown-key semantics of every write verb (`replace()` deletes keys the model does not declare; `save()`/`update()` preserve them), the `extra='allow'` round-trip recipe for adopting existing TinyDB files, and doctested migration patterns (add/rename/remove fields, type changes, versioned migrations).
- Docs: a "Security considerations" usage page — database-file permissions, untrusted input in queries (regex conditions are a ReDoS vector) and updates (mass assignment via `extra_keys="allow"`), and the trusted-input requirement for YAML database files.
- Lifecycle hooks: `before_write(fields)` (runs before every instance-level write — `insert()`, each document of `insert_multiple()`, `save()`, `replace()`, `upsert()`, and `patch()`) and `after_read()` (runs after every read that materializes an instance, with the real `id` set). `before_write()` receives the model-field mapping about to be written — every field on a whole-model write, the caller's fields on `patch()`, never `id` or `revision_id` — and returns the fields it wants to add or override, which are validated, persisted, and set on the instance; returning `id`, `revision_id`, or a non-model key raises. Assigning to `self` in the hook is not supported: `patch()` writes only named fields, so such assignments are silently dropped — return the mapping instead. Raising aborts the write with nothing written. Both are overridable no-ops and `super()`-chainable; the table-level `update()` and `update_all()` write by condition with no instance and fire neither hook, so a mass write does not bump an `updated_at` stamped in `before_write()`.
- `Unique` field marker (`email: Annotated[str, Unique()]`) and `UniqueConstraintError` — duplicate values are refused on `insert()`/`insert_multiple()`/`save()`/`replace()`/`upsert()`/`patch()` with a check-then-write scan (in-process; `None` exempt; the bulk `update()` path is the documented bypass). `insert_multiple()` checks the whole batch — against the table and against itself — using a single table scan indexed by comparison key, so a constrained bulk load costs one storage read rather than one per document and stays linear in the batch size. The Models page documents the cost, since TinyDB has no indexes and every enforcing write is O(documents).
- Composite unique constraints: the `constraints=(UniqueConstraint("follower_id", "followee_id"),)` class kwarg (a config key — inherited nearest-wins, late-bindable via `bind()`/`unbind()`) enforces uniqueness over field tuples on the same write paths as `Unique`, participating only when every constrained field is non-`None` (SQL composite `UNIQUE`/`NULL` semantics). An optional `key=` callable — also new on the `Unique` marker (`Unique(key=str.casefold)`) — normalizes the comparison (case-insensitive pairs, one-entry-per-day keys) while stored values stay untouched; when a key produced the match, the error message shows the computed comparison key alongside the raw values. Declarations naming `id` or a non-model field raise the new `ConstraintFieldError` at class definition or `bind()` time instead of silently never enforcing. `patch()` checks the stored document merged with the patch, so patching one member of a pair cannot sneak into an already-taken tuple.

- `patch()` — instance-level partial update: validates the given fields, writes only those fields to the stored document by id (atomic, merged-result-validated like `update()`), and syncs the instance after the write succeeds. Closes the lost-update trap of whole-document mutate-then-`save()` and the instance/storage drift of table-level `update(doc_ids=...)`.
- `unbind()` — the inverse of `bind()`: detach a late-bound database, reset `table_name` to its derived default, or clear any other config key this class set (no arguments clears them all). Values inherited from base classes resurface. Built for the test-fixture setup/teardown pattern.
- `bind()` now covers every configuration key: `validate_writes=` and `shadowed_fields=` join `database=` and `table_name=`.
- `shadowed_fields` configuration key and `ShadowedFieldError` — loud, definition-time detection of fields that would break the `Model.field` query shorthand, with an explicit per-class opt-out.

- `SelectorError` and `DocumentAlreadyExistsError` — completing the curated exception surface: no raw TinyDB or bare built-in exception leaks through tinydantic's public API.
- `validate_writes` configuration key (class kwarg, inherited like `database=`/`table_name=`): controls write-boundary re-validation; defaults to `True`.
- `UnknownUpdateFieldError` — raised for unknown keys in update mappings; a `TinydanticUserError` naming the offending keys and the escape hatch.

## [0.4.0] - 2026-07-10

### Changed

- **BREAKING:** `insert_multiple()` now mirrors `insert()`: each passed-in model's `id` is set in place to the id TinyDB assigned, and the same instances are returned in insertion order (`list[Self]`, previously `list[int]`). Read ids from the returned models' `id` attributes.
- **BREAKING:** `update()` and `update_multiple()` now give mapping values the same treatment `insert()` and `save()` give whole models: values that name model fields are validated against the field's type (invalid values raise `pydantic.ValidationError`) and serialized to JSON-safe primitives before reaching storage, so rich values such as `datetime` round-trip instead of corrupting JSON storage. Keys that are not model fields, and transform callables, pass through unchanged.
- **BREAKING:** `DocumentNotFoundError` and `DocumentIDRequiredError` now take keyword arguments when constructed directly, and their messages name the model, table, document id, and operation (for example `No document with id 42 in table 'books' (model 'Book')`).

### Added

- `get_or_raise()` — the strict counterpart to `get()`: fetches a single document by condition or `doc_id` and raises `DocumentNotFoundError` instead of returning `None` when no document matches.
- `count()` can now be called with no arguments to count all documents in the table.
- `q()` now accepts a field name as a string (`q("search") == "fuzzy"`), the escape hatch for querying fields whose names collide with model methods such as `search` or `get`.

## [0.2.0] - 2026-07-06

### Changed

- **BREAKING:** The base class is now `TinydanticModel` (previously `Document`). Configure it with class keyword arguments—`database=` and `table_name=`—and rebind a model to a different database at runtime with `bind()`.
- **BREAKING:** A document's `id` is now included in `model_dump()`, and stored documents are serialized in JSON mode. Calling `save()` on an instance that has never been persisted now inserts it.
- **BREAKING:** `get()` selector arguments have been renamed to `doc_id` and `doc_ids` and are now keyword-only. Passing more than one selector raises `ValueError`, and `get(doc_ids=...)` returns a `list[Self]`, silently skipping any ids that are not found.
- **BREAKING:** The minimum supported Python version is now 3.11 (previously 3.8). PyPy is no longer claimed as a supported runtime.
- **BREAKING:** `DocumentIDRequiredError` no longer subclasses `ValueError`. All library exceptions now derive from a common `TinydanticError` base.
- Tooling: the project build backend moved from hatch to uv with `poethepoet` task running and `uv_build` (versioning is now static, managed by commitizen); the documentation engine is now ProperDocs, and the docs site gained eight new usage pages.

### Added

- A full Table API surface: `search`, `contains`, `update`, `update_multiple`, `upsert`, and `remove`.
- A `delete()` method for removing documents.
- Convenience lookups: `get_by_cond`, `get_by_id`, and `get_by_ids`.
- A `q()` query helper.
- Error classes are now exported from the package root.
- A `py.typed` marker so downstream type checkers pick up tinydantic's type hints.

### Fixed

- `save()` no longer crashes when called on an instance that has not yet been persisted.
